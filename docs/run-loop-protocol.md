# 自动跑环协议与状态机

本文记录 `session-20260901-184658-672-跑环sqlite.sqlite` 的回放结论。实现只重建已由录制确认的报文结构；动态请求序号、时间戳和服务端传送确认串均取实时值，不重放样本值。

## 任务规则

- 任务 ID：`140000000`。
- 柳先元领取功能：`140000001`；交付并领取下一环：`140000002`。
- 每轮 20 环，本次可设置 1–6 轮（最多 120 环）；实际每日可接取次数以服务端为准，收到次数用尽提示时停止。旧录制中显示的每日四轮不再作为本次计划的硬编码上限。
- `SC 0x003E` 包含环号、任务描述、目标进度和交付 NPC。交付请求后的 `SC 0x003F`（任务 ID `140000000`）确认当前环已移除；第 20 环在此时计入完成轮数，随后需要重新访问柳先元接取。
- 任务正文既支持直接 UTF-8，也支持 Base64 包裹的 HTML。解析器先解码 Base64、去除 HTML 标签，再识别“将……”道具环或“去……消灭……”战斗环。
- HTML 任务链接中的 `event:x,y,m,n` 是优先数据源：分别提供坐标、地图 ID 和 NPC ID。只有旧样本没有该链接时才回退到运行时实体目录按 NPC 名称查找。

## 已确认报文

| 方向 | Opcode | 含义 | 关键字段 |
| --- | --- | --- | --- |
| C→S | `0x00B5` | 点击任务链接/前往目标 | 模式 `FE`、NPC ID 字符串、地图 ID 字符串、`x=y`、实时序号 |
| C→S | `0x0016` | 访问 NPC/地图入口 | NPC ID、实时序号 |
| C→S | `0x0017` | 选择 NPC 功能 | NPC ID、功能 ID 字符串、实时序号 |
| C→S | `0x004C` | 确认传送 | 本次服务端 context、随机 token、`ok`、零字段、实时序号 |
| C→S | `0x00C1` | 地图走步 | 64 位 Unix 毫秒、地图 ID、X×16、Y×16、实时序号；固定 24 字节 |
| C→S | `0x002E` | 一键恢复 | action=`0x0321`、value=`1`、arg1=`3`、arg2=`0`、实时序号；固定 24 字节 |
| S→C | `0x003E` | 任务及进度 | 任务 ID、标题、描述、`目标 (当前/需要)` |
| S→C | `0x003F` | 移除任务 | `u16` 长度前缀的任务 ID；仅处理 `140000000` |
| S→C | `0x0055` | 当前地图 | 地图 ID、UTF-8 地图名、出生点缩放坐标 |
| S→C | `0x001C/0x006A` | 地图实体表 | 实体 ID、UTF-8 名称、类型、坐标；用于运行时学习 NPC ID |

走步包布局：

```text
00 18 00 C1 | epoch_ms:u64 | map_id:u32 | scaled_x:u16 | scaled_y:u16 | sequence:u32
```

一键恢复布局：

```text
00 18 00 2E | 00 00 03 21 | 00 00 00 01 | 00 00 00 03 | 00 00 00 00 | sequence:u32
```

对未录制且无法从运行时实体表解析的 NPC ID 或战斗地图入口，状态机会停止并明确记录原因，不发送猜测 ID。

## 自动化状态机

战斗巡逻核心已提取到 `src/Protocol/AutomaticCombat.cs` 的 `AutomaticCombatPatrol`；跑环和“自动战斗”独立入口共用原协调器的网络上下文、实时序号与走步/恢复定时器。跑环的任务判断、完成交付和无进度重新到图重试保持原样。独立模式仅在当前地图运行，通过服务端 `0x002C` 战斗提示刷新无遇怪计时，不发送额外的回合推进包；不会因跑环任务更新而自动旅行或交付。默认参数仍来自 `RunLoopWalkOptions`（当前代码走步间隔为 200 ms、恢复为 4000 ms）。

1. 等待真实游戏连接和任一带实时序号的 C→S 游戏包。
2. 若已有新鲜的 `0x003E` 当前任务，直接解析；否则前往柳先元并选择领取功能。
3. 道具环：从 Base64 HTML 的任务链接读取 NPC ID、地图 ID 和坐标 → 发送任务链接 → 动态确认传送 → 访问 NPC → 校验功能列表存在 `140000002` → 提交。
4. 战斗环：若目标在 42 张地图目录中，使用该地图已录制蟠龙图腾的 `0x00B5` 旧任务链接直接到图；目录外仍沿已确认入口链切图。到图后读取地图可行走格，固定最多 4 个相邻有效点，按 A→B→C→D→C→B→A 循环，每 250 ms 发送 `0x00C1` 走步包，直到任务进度达到要求。可用点不足 4 个时使用至少 2 个相连点；缺少地图数据或无法形成路线时等待最多 10 秒后停止。
5. 战斗等待期间每 4 秒发送一次 `0x0321` 一键恢复。任务进度达到要求后停止走步/恢复并前往交付 NPC。
6. 发送 `140000002` 时记住待交付环号；收到该任务的 `0x003F` 后清空任务缓存、累计交付次数。普通环等待下一环任务；第 20 环累计一轮，未达计划则返回尚其村柳先元，访问 NPC `93290` 并选择 `140000001`。最后一轮直接结束，无需等待额外的第 1 环。
7. 删除包按待交付请求去重；等待下一环时只接受预期环号，旧的 `0x003E` 更新和 `0x003D` 任务列表不能恢复已交付任务。运行时任务列表与增量任务更新使用相同的检查流程。

## 第 20 环缓存修复（2026-09-10）

原始跑环录制的 capture ordinal `654` 是向刘兴提交第 20 环的 `140000002` 请求；`656` 仍是旧第 20 环更新，`662` 才是 `00 0F 00 3F 00 09 31 34 30 30 30 30 30 30 30` 删除任务。之后玩家返回柳先元，在 `721` 发送 `140000001`，`727` 才收到新一轮第 1 环。

此前忽略了删除包，且任务列表按环号大小保留缓存，导致第 20 环无法被下一轮第 1 环正确替换。现在以服务端移除任务作为交付确认，并主动重新接取。回归测试通过模拟传输执行六轮共 120 次交付，覆盖旧任务回发、重复删除、其他任务删除、迟到的任务列表，以及最后一轮无需再次接取即可结束。该测试不会向真实游戏服务器发包。

## 走步配置（2026-09-11）

`src/Protocol/RunLoopAutomation.cs` 的 `RunLoopWalkOptions` 构造函数集中定义默认值；修改后重新编译并重启启动器生效。调用方也可以通过 `new RunLoopAutomationCoordinator(service, options)` 为单个客户端传入配置，协调器会校验并复制配置。

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| `StepIntervalMs` | `250` | 周期走步发包间隔（毫秒） |
| `InitialDelayMs` | `200` | 开始遇怪后的首次调度延迟（毫秒）；还需等待有效地图数据 |
| `PatrolPointCount` | `4` | 固定往返点数上限，允许 2–16 |
| `MapDataWaitTimeoutMs` | `10000` | 等待有效地图数据/路线的最长时间（毫秒） |
| `NoProgressTimeoutMs` | `75000` | 任务进度持续不变时重新到图的等待时间（毫秒） |
| `RecoveryIntervalMs` | `4000` | 自动恢复 HP/MP 的间隔（毫秒） |
| `MaximumHuntRetries` | `3` | 无进度后重新到图的最大次数 |

路线只在开始遇怪或地图数据更新时生成，定时器沿同一路线反向往返，避免逐次累加偏移而越走越远。无进度等待使用独立计时器，不随走步间隔缩短。测试以模拟传输检查真实定时器输出的走步包、坐标往返顺序、请求序号递增以及停止后不再发包。

## 与地图/飞行 API 的组合边界

独立调用可使用 `MapTeleportAutomationCoordinator.TeleportViaTotem(...)` 和 `FlyTo(mapId,x,y)`。自动跑环本身已经持有工作台自动化独占锁，因此不会嵌套启动另一个协调器；它直接复用 `TianshuMapTeleportCatalog.GetTotemTravelTarget`、`TianshuBountyProtocol.BuildTravelRequest` 等无状态底层接口，并由跑环状态机统一维护实时序号和到图确认。

这意味着目前的自动跑环已经可以覆盖：Base64 HTML 道具交付、目录内战斗地图到图、NPC 对话、交付下一环、持续走步遇怪和 4 秒恢复。仍会安全停止的情况是：任务类型文本发生新格式变化、目标地图不在图腾目录也没有已录制入口链、服务端没有返回任务链接中的 NPC ID、或服务端功能列表不含已确认的跑环功能 ID。遇到这些情况应补录对应原子操作，不会猜测发包。

## SQLite 会话命名与连接释放

原子操作停止只结束原子步骤区间，整场 Winsock 抓包仍会继续，因此不能直接关闭当前会话库。活动会话改名在写线程内执行：先清空队列、checkpoint WAL、关闭写连接、清理 SQLite 连接池，然后移动主库及 `-wal/-shm/-journal` 并重新打开新路径。

移动现在是事务式的并对短暂占用重试：任何伴随文件失败都会倒序移回已经移动的文件，避免出现“主库已改名、状态仍指向旧路径”的半完成结果。

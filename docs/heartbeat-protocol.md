# v5 心跳协议、30 秒周期与校验状态机

## 结论

本次样本确认游戏连接使用一组服务器驱动的挑战/应答心跳：

```text
SC_SERVER_PING  0x0053  S→C
        │  客户端收到后立即计算
        ▼
CS_CLIENT_PING  0x0042  C→S
```

- `SC_SERVER_PING` 的服务器时间戳相邻差值为 `29,999–30,001 ms`，20 个连续间隔的平均值正好是 `30,000 ms`。因此 30 秒可以视为服务端心跳周期。
- 客户端不应从登录完成时刻自行启动 30 秒发送定时器。原客户端只在收到 `0x0053` 后立即回复 `0x0042`；这样不会因本地定时器漂移而逐渐错位。
- 用户提供的文本片段包含 `counter=1..20` 的 20 组连续应答。与该片段对应的完整 SQLite 会话还保留了片段之前的 `counter=0` 初始化包；它携带后续校验所必需的加密种子。
- `0x0053` 中看似随机的十进制字符串，在 `auth_flag != 0` 时并不参与本轮计算。真正的校验值是一个跨心跳持续演进的 32 位状态。
- 世界/系统消息 `SC_SYSTEM_MESSAGE (0x0029)` 与大量 HTTP 资源连接的 `Close Unknown` 都不是心跳。分析时必须按游戏连接、方向和 opcode 过滤。

分析来源：用户提供的 `pasted-text.txt`，以及本机匹配会话 `bin/Release/data/instances/8c552d41a6674c95904c3235bd801c96/sessions/session-20260902-103818-191.sqlite`。文档中的算法又与本机缓存的原版 `GameWorld.swf` 客户端实现进行了交叉核对。

## 公共帧格式

所有整数和帧长度均为大端序：

```text
u16 frame_length       // 包含本字段和 opcode
u16 opcode
byte body[frame_length - 4]
```

字符串为：

```text
u16 utf8_byte_length
byte utf8_bytes[utf8_byte_length]
```

TCP 没有消息边界，读取端必须缓存半包并按 `frame_length` 拆帧，也必须允许一次 `recv` 中出现多个完整帧。

## SC_SERVER_PING (0x0053)

正文结构如下：

```text
offset  size  type    field
0x04    4     i32     heartbeat_counter
0x08    4     u32     server_time_high
0x0C    4     u32     server_time_low
0x10    4     i32     city_rate
0x14    2     i16     auth_flag
0x16    2     u16     auth_text_length = N
0x18    N     UTF-8   auth_text
0x18+N  2     u16     system_time_length，样本恒为 16
0x1A+N  16    UTF-8   system_time，格式 yyyy-MM-dd HH:mm
```

`server_time_high` 和 `server_time_low` 组成毫秒 Unix 时间：

```text
server_epoch_ms = (uint64(server_time_high) << 32) | server_time_low
```

原 Flash 客户端把这两个 32 位字段传给 `updateServerTime()`，并在回包中逐字节回显。不要先转换为本地 `Date` 再编码，否则可能发生精度或时区错误。

字段含义：

- `heartbeat_counter`：服务器心跳计数；初始化包为 0，之后逐次加 1。
- `city_rate`：原客户端直接传给城市界面的 `setRate()`。初始化值为 1000，后续样本为 6–18。它不是校验算法的操作数。
- `auth_flag`：值为 0 表示“首次发送校验种子”；非 0 时客户端不会读取 `auth_text` 来修改校验状态。
- `auth_text`：首次包中是 RC4 密文的十六进制文本；普通周期中是可变长度的十进制文本，但原客户端忽略它。
- `system_time`：供界面显示的服务端分钟字符串，不参与校验。

因此普通包长度随 `auth_text` 长度变化。固定关系为：

```text
frame_length = 42 + auth_text_length
```

样本普通包的 `auth_text` 长度为 8、9 或 10，所以帧长分别为 50、51 或 52；这不是三种不同心跳协议。

## CS_CLIENT_PING (0x0042)

回包固定为 24 字节：

```text
offset  size  type  field
0x00    2     u16   frame_length = 24
0x02    2     u16   opcode = 0x0042
0x04    4     i32   heartbeat_counter（原样回显）
0x08    4     u32   server_time_high（原样回显）
0x0C    4     u32   server_time_low（原样回显）
0x10    4     u32   transformed_auth_code
0x14    4     i32   client_message_sequence
```

最后的 `client_message_sequence` 不是心跳计数。原客户端的统一发包器会给 `20 <= opcode < 2000` 的每个客户端请求追加一个共享序号；到 `int32.max` 后回到 1。样本初始化心跳的序号已经是 10，随后是 11–30，因为进入游戏期间已有其他请求消耗了 1–9。第三方客户端必须让心跳与其他请求共用同一个序号发生器。

## 校验种子与变换算法

### 1. 初始化种子

当 `auth_flag == 0` 时：

1. 把 `auth_text` 当作偶数长度十六进制字符串解码为字节。
2. 使用 RC4 解密，密钥的 ASCII 文本为：

   ```text
   The.tianshu.game.need.your.support
   ```

3. 明文是十进制整数文本；按十进制解析为当前 `auth_code`。

本样本初始化向量：

```text
cipher text : 0cd6e9fe0a518c86ca
RC4 plaintext: 484026905
initial code : 0x1CD9AA19
```

### 2. 每轮变换

包括初始化包在内，每收到一次 `SC_SERVER_PING`，都先变换一次，再把结果写进 `CS_CLIENT_PING`：

```text
sum       = (auth_code + 931209513) mod 2^32
auth_code = rotate_right_32(sum, 3)
```

等价 TypeScript：

```ts
const sum = (authCode + 931_209_513) >>> 0;
authCode = ((sum >>> 3) | ((sum & 0x7) << 29)) >>> 0;
```

原客户端实现本质为：

```text
param += 931209513
return param >>> 3 | (param & 7) << 29
```

所有加法和移位必须保持 32 位回绕语义。普通心跳的 `auth_text` 不应混入公式。

### 3. 首两轮逐字节验证

初始化请求：

```text
00 3C 00 53 00 00 00 00 00 00 01 A0 5F FB F5 54
00 00 03 E8 00 00 00 12 30 63 64 36 65 39 66 65
30 61 35 31 38 63 38 36 63 61 00 10 32 30 32 36
2D 30 39 2D 30 32 20 31 30 3A 33 39
```

解密得到 `484026905`，第一次变换得到 `0x4A8B5968`，对应实录回包：

```text
00 18 00 42 00 00 00 00 00 00 01 A0 5F FB F5 54
4A 8B 59 68 00 00 00 0A
```

下一轮再次变换得到 `0x30418F52`：

```text
00 18 00 42 00 00 00 01 00 00 01 A0 5F FC 6A 84
30 41 8F 52 00 00 00 0B
```

## 周期和时钟细节

文本片段中 `counter=1..20` 的服务端线内时间戳为：

```text
1788316772996, 1788316802996, ... , 1788317342996
```

19 个间隔最小 29,999 ms、最大 30,001 ms、平均 30,000 ms。服务端时间比抓包电脑显示的本地时间约快 3.17 秒；这是两台时钟的偏差，不影响协议。回包必须回显包里的 high/low 字段，不能用 `Date.now()` 代替。

`SC_SYSTEM_MESSAGE (0x0029)` 大约出现在某些分钟的第 57 秒，但心跳仍保持在第 29.82/59.82 秒附近，所以世界消息不会重置、触发或延迟心跳周期。

## 正确的客户端状态机

```text
连接游戏服
  └─ 等待 SC_SERVER_PING
       ├─ auth_flag == 0
       │    └─ RC4 解出初始 auth_code
       ├─ 尚无 auth_code
       │    └─ 停止：说明漏掉了初始化包，不能猜测
       └─ auth_code = ROR32(auth_code + 931209513, 3)
            ├─ 原样回显 counter 和 server_time high/low
            ├─ 从全局发包器取得下一个 message_sequence
            └─ 立即发送 CS_CLIENT_PING
```

实现要求：

- 游戏服连接建立后立刻开始拆帧，不能等角色进入地图后才注册心跳处理器，否则可能漏掉初始化种子。
- 不另开周期发送器。可设置 65 秒只读 watchdog：超过两个周期未收到 `0x0053` 时报警，但不要凭空补发 `0x0042`。
- 校验状态按连接隔离；重新登录必须丢弃旧连接的种子和序号。
- 收到初始化包之前若先收到普通包，应明确报“漏掉 bootstrap”并停止，不能从普通 `auth_text` 猜种子。
- 日志可记录 counter、时间、校验值和耗时，但不需要保存登录票据或密码。

## TypeScript 对应实现

本次新增实现位于：

- `headlessclient/src/protocol/heartbeat.ts`：RC4、种子解析、32 位变换、请求解析和回包构造。
- `headlessclient/src/protocol/binary.ts`：大端读写、TCP 半包/粘包拆帧、共享客户端序号。
- `headlessclient/src/protocol/protocol.test.ts`：初始化包与第 1 个普通包逐字节断言，并用实录的 21 个校验值验证整个状态链。

网页客户端的 Node 网关收到 `0x0053` 后同步计算并发送 `0x0042`，网页只展示脱敏后的帧元数据和心跳状态。
